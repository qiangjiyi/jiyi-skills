# wechat-article-production 深度 Review（修订版 v2）

> 复核日期：2026-08-13
> 复核背景：第一版（v1）基于错误的 Skill 挂载路径（`~/.baoyu-skills/`、`~/.claude/skills/`）做了判断，用户指出所有下游 Skill 实际已挂载在 `~/.agents/skills`。本版改用真实挂载路径与真实下游 Skill 源码逐条复验，并修正了 v1 中**不准确的三条结论**。

## 0. 与第一版（v1）的差异 / 撤回项

| v1 结论 | 复核结果 | 说明 |
|---|---|---|

## 1. 已确认的真问题（按阻断性排序）

### 🔴 B1. `init` 必崩：`randomUUID is not defined`（阻断性，已实测复现）
- **位置**：`scripts/execution-manifest.mjs` 第 279 行
  ```js
  run_id: args["run-id"] || `wechat-${timestamp...}-${randomUUID().slice(0, 8)}`,
  ```
- **问题**：`randomUUID` 未被 import。本文件只从 `shared.mjs` 导入了 `parseArgs/required/list/packageRelativePath/atomicWrite`，没有 `node:crypto` 的 `randomUUID`。
- **触发路径**：`prepare-package.mjs` 调用 `init` 时**从不传 `--run-id`**（line 47–63 无该参数），于是每次 prepare 都会执行到这个 fallback → 抛 `ReferenceError` → prepare 直接失败，整个流水线起步即死。
- **实测**：
  ```
  $ node execution-manifest.mjs init --file .../execution-manifest.json --package-dir ... --execution-stages prepare,... --illustration-skill jiyi-little-dancer-illustrations --native-dispatcher Skill --native-dispatcher-available true
  {"ok":false,"error":"randomUUID is not defined"}
  ```
- **修复**：在文件顶部 `import` 中加入 `randomUUID`（`import { randomUUID } from "node:crypto";`）即可。一行改动。

### 🔴 B2. typeset 阶段契约断裂：gzh 产物文件名与 wechat 期望不符（阻断性）
- **位置**：`references/stage-dispatch-rules.md` 的 `typeset` 段（line 133–135）只说"加载 gzh-design-skill，输入 article-illustrated.md / formatted.md，父流程检查结果"，**没有任何把产物改名/搬移到约定路径的步骤**。
- **事实**：`gzh-design-skill/SKILL.md` 第 6 步明确定义输出为：
  - 干净正文：`{原文件名}_排版_{主题中文名}({英文标识}).html`
  - 预览页：`{...}_预览.html`（由 `wrap_preview.py` 生成）
  - **从不产出 `article.html` / `article-preview.html`**。
- **冲突**：wechat 的 `requiredFiles`（typeset）与 `checkHtml` 硬要 `article.html`/`article-preview.html`（`validate-package.mjs` line 167–168；`execution-manifest.mjs` line 150–151）。
- **结果**：typeset 完成后，validate 的 `file:article.html` 检查必然失败 → `ok:false` → 无法 publish。
- **对照 format 阶段**：format 有专门的 `normalize-format-output.mjs` 做 `source-*.md → analysis.md/formatted.md` 重命名；**typeset 缺少对应的 `normalize-typeset-output.mjs`**。这正是"不顺"的核心断裂点。
- **修复方向**：新增一个 normalize 脚本（或在该阶段 dispatch 指令里明确要求），把 gzh 的 `{原文件名}_排版_*.html` 复制/重命名为 `article.html`、`{...}_预览.html` 重命名为 `article-preview.html`，再跑 validate。

### 🟠 B3. `illustrations/ip-reference.png` 无人播种（小舞伴模式必卡）
- **事实**：`validate-package.mjs` 对 jiyi 模式在 `requiredFiles`（line 156–161）与 `checkIllustrationHandoff`（line 250–257）强制要求 package 内存在 `illustrations/ip-reference.png` 且 `reference_asset.package_path` 指向它、`used_for_identity: true`。
- **但**：
  - `prepare-package.mjs` 只复制 `source.md` + 初始化 manifest，**不复制/生成** `ip-reference.png`。
  - `jiyi-little-dancer-illustrations` 的脚本（`finalize-handoff.mjs` 等）只**读取** `illustrations/ip-reference.png` 校验其存在；图像后端实际用的是 `--reference-source <SKILL_ROOT>/assets/little-dancer-reference-sheet.png`（jiyi 自己的资产），**从不把参考图写入 package**。
  - 全仓库 grep `copyFile`/`writeFile` 生成 ip-reference：**无**。
- **结果**：小舞伴模式下，`Illustrate` 阶段 handoff 校验永远因 `illustrations/ip-reference.png` 缺失而失败。
- **修复方向**：让 `prepare-package.mjs`（或 format 之后）把 jiyi 的资产 `assets/little-dancer-reference-sheet.png` 复制为 `illustrations/ip-reference.png`；或在 SKILL.md dispatch 中明确由编排者在 illustrate 前放置该文件。当前既无脚本也无明确人工步骤，是隐性断点。

### 🟠 B4. `native-skill-transcript` 检查跨工具硬耦合（在 WorkBuddy 下高危）
- **位置**：`validate-package.mjs` `findNativeSkillCalls`（line 301–361）硬编码 `resolve(homedir(), ".claude", "projects")`，扫描该目录下 `.jsonl` 里是否含 `packageDir` 与 `"name":"Skill"`。
- **问题**：该格式是 Claude Code 的 transcript 约定。在当前 WorkBuddy 宿主下，原生 Skill 调用不会写入 `~/.claude/projects/*.jsonl`，导致 `transcript.calls` 几乎必然为空 → 凡是 `invocation.kind === "native-skill"` 且 `status === "completed"` 的阶段（dispatch 规则要求 stage-start 带 `--invocation-kind native-skill`），`native-skill-transcript` 检查都会失败 → validate 挂 → 发布被卡。
- **修复方向**：该检查应降级为 **warning** 而非 fatal；或改为读宿主真实 transcript 位置。至少应支持通过环境变量/参数指定 transcript 目录，并在目录不存在时 skip（而非 fail）。

## 2. 真实存在的脆弱点（非硬崩，但高度依赖编排者纪律）

### C1. 多个阶段的"产物搬移"完全靠编排者手动遵守 dispatch 规则
- format：`baoyu-format-markdown` 输出 `source-analysis.md`/`source-formatted.md`（package 根），必须经 `normalize-format-output.mjs` 改名；若编排者漏跑 normalize，validate 的 `analysis.md`/`formatted.md` 缺失 → 失败。
- cover：`baoyu-cover-image` 输出 `cover.png`（在其 outputs 目录），dispatch 要求搬进 `cover/cover.png`，且要产出 `cover/prompt-validation.json`。**没有 cover 专用的 normalize/copy 脚本**，全靠人工 `mv`。漏搬即失败。
- illustrate / typeset：同理依赖人工按约定路径落盘。
- **根因**：wechat 只在 format 做了脚本化归一化，cover/typeset 没有，导致流水线"半自动半手工"，极易出现"下游跑完了但 validate 找不到文件"的不顺。

### C2. `normalize-format-output.mjs` 用 `rename` 而非 `copy`
- line 25 `await rename(derived, canonical)`。若 baoyu 的输出不在 package 根（dispatch 要求"在 package 根目录交付"，但若下游实际写到别处），rename 会因跨设备/路径失败或找不到源。属边界脆弱，正常路径 OK。

## 3. 次级 / 精确化的问题（原 v1 表述需修正）

### M1. publish 脚本（修正表述）
- ✅ **有 `--yes`**：`--yes` 存在且生效（`confirm()` line 357 `if (args.yes) return`，跳过 stdin 确认）。**v1 说"无 --yes"是错误的。**
- ⚠️ **非 TTY 挂起**：未传 `--yes` 时，`confirm()` line 358 创建 `readline` 接口等待 `rl.question` 输入。在自动化 / 非 TTY 环境（如 CI、子进程无 stdin）会**永久挂起**。结论应为："自动化发布必须传 `--yes`，否则卡在 stdin 确认。"
- ⚠️ **`--title` 必填但无校验、无自动提取**：`args.title` 直接进 `article.title`（line 392/426），但 `main()` 不校验其存在；缺失时静默传 `undefined` 给公众号 API，易被判非法。dispatch / usage 也未说明标题应从 manifest 还是 HTML `<title>` 提取。建议：缺失时从 `formatted.md` frontmatter `title` 或 `article.html` 的标题自动提取并校验非空。
- ⚠️ **dry-run 写 `ok:false` 语义误导**：line 400 `writeJsonAtomic(args.resultFile, { ...plan, ok: false, dry_run: true })`。dry-run 成功时也写 `ok:false`，下游若按 `ok` 判成功会误判失败。建议 dry-run 成功写 `ok: true, dry_run: true`。

### M2. `execution-manifest.schema.json` 是死文件（维持 v1 结论，仍准确）
- 仓库带 JSON Schema，但 `execution-manifest.mjs validate` 用自己手写的 `validateManifest()`，**从未加载该 schema**（grep 确认仅 self-reference + 本 review 提及）。两处规则会漂移。建议二选一：用 ajv 真正加载，或删文件避免误导。

### M3. `html-images-syntax` 检查名不副实（维持 v1 结论）
- `validate-package.mjs` line 286：`html-images-syntax` 实际只检查 `inspection.errors` 里是否含 "img" 字样，并不真正校验 `<img>` 的 src 是否为可解析的 ASCII 引号属性。标签与实现不符，属于误导性 check。

## 5. 一句话总结
第一版最大的失误是查错了 Skill 挂载路径，导致"下游没装"等三条结论失真。**真实的根因不在"装没装"，而在"契约对不对得上 + 一个必崩的 import bug"**：`randomUUID` 缺失让 prepare 起不来（B1）；gzh 输出文件名与 wechat 期望的 `article.html` 对不上且缺归一化（B2）；小舞伴参考图无人播种（B3）；transcript 检查硬编码 Claude Code 路径在 WorkBuddy 下必挂（B4）。这四处才是"执行起来各种问题、不顺畅"的真正来源。
